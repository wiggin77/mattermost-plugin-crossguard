# Envelope sequence and epoch

## Context

Inbound sync messages are best-effort ordered today. The upstream
shared-channels sender batches Posts and Reactions for a channel into a
single `SyncMsg`, but when the sender's cursor splits a post and a
related reaction across two consecutive batches, the transport can
reorder them. All four providers (NATS core, Azure Queue, Azure Blob,
Azure Service Bus) preserve order on the happy path but can reorder
under retry, abandon, or list-blob enumeration. The receiver applies
per-entity errors from `mmModel.SyncResponse` to a warning log
(`inbound.go:195-199`) and then returns `nil`, so the transport ACKs
and the failed entity is lost.

The previous pre-shared-channels plugin had a retry queue
(`server/retry_queue.go`, `server/retry_dispatch.go`, both deleted in
commit `e37edd5`) that absorbed exactly this case: a reaction whose
post mapping was not yet present was held in memory and retried for
up to two minutes. The refactor assumed intra-`SyncMsg` ordering was
sufficient and removed the queue. It is not sufficient under
cross-envelope reordering.

The fix is to give each `sync_msg` envelope a per-channel monotonic
`Sequence` plus a sender-chosen `Epoch` nonce, and to give the receiver
a bounded in-memory reorder buffer that holds out-of-order envelopes
until the gap fills or a deadline expires. This is the same shape as
RTP/QUIC packet numbering: monotonic sequence over a no-feedback
transport, with reorder and gap detection but no retransmit request.
True message loss remains possible but is detected and audited rather
than silent.

## Scope

In scope:

- Add `Epoch` (UUID) and `Sequence` (uint64) to `TransportEnvelope`,
  populated on `type="sync_msg"` envelopes only.
- Sender assigns sequence per `(outboundConnName, channelID)`,
  starting at 1 for each new epoch. Counter persisted in KV.
- Receiver maintains in-memory per-`(remoteID, channelID)` cursor and
  reorder buffer. Cursor is checkpointed to KV.
- Inbound subscription model moves to single-active-receiver-per-
  connection via the Mattermost cluster service. NATS queue groups
  are kept as a defense-in-depth tiebreaker during leadership handoff.
- Audit logging on every state transition: gap detected, gap filled,
  gap timed out, buffer overflow, duplicate suppressed, epoch reset,
  active-node elected, active-node stepped down.

Out of scope:

- Retransmit request from receiver to sender. There is no back-channel
  on any provider, and adding one is a much larger change.
- Cross-channel ordering. Different channels are independent streams
  by design.
- Cross-connection ordering. Different outbound conns are independent.
- Attachments and profile images. Those travel on the file path
  (`UploadFile` / `WatchFiles`), not on `TransportEnvelope.SyncMsg`,
  and have no causal dependency on sync_msg ordering.
- `test` envelopes. Diagnostic only; sequence would add noise.

## Wire format

We have not yet shipped the current XSD, so this is folded into the
v1 schema rather than bumped to v2. The next compliance review covers
both the plugin-owned wire types and the sequence/epoch fields.

Two new envelope-level optional elements, siblings of `Timestamp`:

```xml
<CrossGuardEnvelope version="1" type="sync_msg">
  <ConnName>nats-low-to-high</ConnName>
  <Timestamp>2026-05-13T10:00:00Z</Timestamp>
  <Epoch>e7c1d2a93f4b4e5a9c8d1b2a3c</Epoch>
  <Sequence>42</Sequence>
  <TeamName>team-a</TeamName>
  <ChannelName>general</ChannelName>
  <SyncMsg>...</SyncMsg>
</CrossGuardEnvelope>
```

- `Epoch`: 26-character Mattermost ID (`[a-z0-9]{26}`), generated by
  the sender at process start via `mmModel.NewId()`. Same format as
  post, channel, user, and team IDs already on the wire; the
  README's existing "All Mattermost IDs are 26 characters of
  `[a-z0-9]`" convention covers it. Same epoch is used for every
  channel on every outbound connection from a given sender instance.
  **Emitted on every envelope type that the sender originates**
  (`sync_msg` and `test`), so a receiver can detect sender restart
  even from a connectivity ping with no payload.
- `Sequence`: unsigned 64-bit integer encoded as decimal. First
  envelope a sender emits to a given channel within an epoch carries
  `Sequence=1`. Counter is per-`(outboundConnName, channelID)`.
  **Emitted on `sync_msg` envelopes only.** Test envelopes have no
  channel scope (their `TeamName` / `ChannelName` are empty) and
  there is no useful counter shared between sync and test traffic;
  giving tests their own counter would add a second persistent
  scope for marginal benefit. Receivers ignore any `Sequence`
  present on a non-`sync_msg` envelope.

Both elements are optional in the schema because:

1. `attachment` and `profile_image` envelope types do not actually
   appear on the SyncMsg path today (file metadata travels on the
   `UploadFile` / `WatchFiles` path); the schema still allows the
   values for forward compatibility.
2. `test` envelopes carry `Epoch` but never `Sequence`.
3. During the staged rollout, sender population lands before receiver
   enforcement. An envelope without `Epoch` / `Sequence` must still
   parse so the receiver's pass-through path keeps working.

When `sync_msg` envelopes carry both `Epoch` and `Sequence`, the
receiver runs the sequencing state machine. When either is absent on
a `sync_msg`, the receiver falls through to the current best-effort
path with an `error_code` audit line so operators can detect a
misconfigured or downgraded sender. When a `test` envelope carries
`Epoch`, the receiver compares it against the current epoch for that
connection and emits a diagnostic audit line on mismatch (sender has
restarted since last sync_msg).

## Phases

The plan is broken into phases that can land as separate PRs. Each
phase is independently testable and reversible. **Phase 1 lands
first as the standalone wire-format change**, then we revisit the
remaining phases in order.

### Phase 1: XSD + example fixtures (this PR)

The minimal wire-format change. No Go code changes. The schema and
examples carry the new optional fields so compliance review can begin
in parallel with the receiver work.

Files:

- `schema/crossguard.xsd`: add `Epoch` and `Sequence` to the
  `CrossGuardEnvelope` sequence, both `minOccurs="0"`. `Epoch` is
  `xs:string` with `xs:pattern value="[a-z0-9]{26}"` matching the
  Mattermost ID convention used for every other ID on the wire.
  `Sequence` is `xs:unsignedLong`.
- `schema/examples/01_post_simple.xml` through
  `schema/examples/11_reaction_custom_emoji.xml`: hand-edit to add
  `<Epoch>` and `<Sequence>` on each. Reuse one epoch ID across
  the 11-envelope timeline (they are one logical sender session) and
  number sequences 1..11 in timeline order. This preserves the
  coherent narrative the README already documents.
- `schema/examples/12_test.xml`: add `<Epoch>` (reusing the same
  epoch ID as the 01-11 timeline so it reads as a connectivity ping
  from the same sender session). No `<Sequence>`. Demonstrates the
  epoch-on-tests rule and gives compliance reviewers a concrete
  example of an envelope with `Epoch` but no `Sequence`.
- `schema/examples/13_membership_change_join.xml` through
  `schema/examples/20_bot_user.xml`: each gets `Epoch` and a
  per-example `Sequence`. These eight fixtures are independent
  scenarios rather than a timeline, so each uses its own epoch ID
  to demonstrate that the receiver state machine treats them as
  separate sender sessions.
- `schema/examples/README.md`: new section explaining what `Epoch`
  and `Sequence` mean, with a pointer to this plan. Note that
  `Epoch` appears on every sender-originated envelope including
  `test`, while `Sequence` appears only on `sync_msg`.

Validation:

- `python3 -c "import xmlschema; s = xmlschema.XMLSchema('schema/crossguard.xsd'); [s.validate('schema/examples/' + f) for f in sorted(os.listdir('schema/examples')) if f.endswith('.xml')]"`
- `go test -run TestExampleFiles ./server/` continues to pass
  byte-for-byte after the example fixtures are updated (the test
  reads them as opaque bytes and compares against marshal output;
  since the wire structs are unchanged in this phase, the round-trip
  test would currently fail; see note below).

**Round-trip test handling for Phase 1.** Because the example
fixtures will contain `<Epoch>` and `<Sequence>` elements that the
current `TransportEnvelope` struct does not know about, the
`TestExampleFiles` round-trip will mismatch. Two options:

1. **Defer Phase 1 fixture changes until Phase 2** (struct fields
   added) so round-trip stays green. This means Phase 1 ships only
   the XSD update.
2. **Land the XSD update and the struct fields together in Phase 1**,
   keeping fixtures aligned. The struct fields are inert (no
   sender populates them, no receiver enforces them); they just
   round-trip the value if present.

Option 2 keeps the example fixtures aligned with the XSD throughout,
and the inert struct fields land in the same PR as the schema they
document. This is what the phase ships.

Concretely Phase 1 also touches:

- `server/transport.go`: add `Epoch string \`xml:"Epoch,omitempty"\``
  and `Sequence uint64 \`xml:"Sequence,omitempty"\`` to
  `TransportEnvelope`, between `Timestamp` and `TeamName` to match
  XSD ordering. No other code changes.
- `server/transport_test.go`: add round-trip test covering
  marshal/unmarshal with both fields set and with both absent.

Validation gate for Phase 1:

- `make check-style` clean
- `go test ./server/... ./server/wire/...` green
- Python `xmlschema` validates all 20 fixtures
- `TestExampleFiles` green after `UPDATE_EXAMPLES=1` regeneration
  if any fixture drift remains

### Phase 2: Single-active-receiver per inbound connection

Move inbound subscription to a cluster-aware single-active model so
the receiver state machine in later phases can run as in-memory
per-process state.

Files:

- `server/inbound.go`: replace direct `provider.Subscribe` at startup
  with an election-gated subscribe. On becoming active for a
  connection, call `Subscribe`; on stepping down, call the provider's
  `Close` (or a new `Unsubscribe` if `Close` is too heavy).
- `server/connections.go`: track active-set per inbound connection.
- New file `server/inbound_election.go`: thin wrapper around the
  Mattermost plugin cluster service for "active node for connection
  X" semantics. Use `KVSetWithOptions` with a TTL on a lease key,
  re-acquire on a timer. (The plugin API does not expose a leader
  primitive directly; the TTL-lease pattern is the established
  idiom in this codebase. Confirm against `pluginapi.Cluster` or
  fall back to KV-lease.)
- New error codes in `server/errcode/codes.go`:
  - `InboundActiveNodeElected`
  - `InboundActiveNodeSteppedDown`
  - `InboundActiveLeaseRenewalFailed`

Out: NATS queue groups stay configured (`connections.go:173` keeps
passing `manifest.Id`). They are not load-bearing anymore but defend
against a split-second overlap window during leadership handoff.

Validation gate for Phase 2:

- New unit test simulating two nodes, only one subscribes at a time.
- Docker dual-server smoke test (`make docker-smoke-test`) passes
  unchanged.

### Phase 3: Sender-side sequence assignment

Make outbound `sync_msg` envelopes carry `Epoch` and `Sequence`.

Files:

- `server/plugin.go`: generate a 26-char Mattermost ID epoch via
  `mmModel.NewId()` at `OnActivate` and store on the plugin struct.
  Persist in KV under `seq_epoch:<outboundConnName>` so a quick
  restart can reuse the same epoch if persistence is recent
  (optional optimization; not load-bearing).
- `server/connections.go` (outbound dispatch path): before publishing,
  look up the per-`(outboundConnName, channelID)` counter, increment,
  stamp the envelope, persist the new counter value. Counter key:
  `seq_counter:<outboundConnName>:<channelID>` storing uint64
  little-endian.
- `server/store/store.go`: add `GetSequenceCounter` /
  `SetSequenceCounter` / `BumpSequenceCounter` (atomic-ish) to the
  `KVStore` interface.
- `server/store/client.go`: implement against `pluginapi.KV` using
  `KVCompareAndSet` for atomic increment.
- `server/store/caching.go`: cache the counter with very short TTL
  (or do not cache; counters are write-mostly per channel and
  caching is unlikely to help).
- New error codes:
  - `SenderEpochAssigned`
  - `SenderSeqCounterIncrementFailed`
  - `SenderSeqCounterPersistFailed`

Validation gate for Phase 3:

- New unit test: assigning sequences across two channels and two
  connections produces independent monotonic streams.
- Integration: capture published envelopes in the docker env and
  assert monotonic sequence per channel-conn.

### Phase 4: Receiver-side cursor and reorder buffer

The substantive correctness change. In-memory per-`(remoteID,
channelID)` state machine.

Files:

- New file `server/inbound_sequencer.go`: the state machine. Methods:
  - `Admit(env *TransportEnvelope) []*TransportEnvelope` returns the
    envelopes ready to dispatch in order, possibly including
    previously buffered ones.
  - `TickGapDeadlines(now time.Time) []*TransportEnvelope` returns
    envelopes whose gap deadline has expired and the buffer has
    given up on. Caller dispatches them with a "gap timed out"
    audit log.
- `server/inbound.go`: between `UnmarshalEnvelope` and channel
  resolution, route through `sequencer.Admit`. On absent `Epoch` or
  `Sequence`, log the audit line and pass through (Phase 1 / 2
  compat).
- Configuration knobs in `server/configuration.go`:
  - `SequencerGapTimeoutSeconds` (default 30)
  - `SequencerBufferMaxEnvelopes` (default 200)
  - `SequencerBufferMaxBytes` (default 50 MB)
- New error codes:
  - `InboundSeqInOrder`
  - `InboundSeqGapDetected`
  - `InboundSeqGapFilled`
  - `InboundSeqGapTimeout`
  - `InboundSeqBufferOverflow`
  - `InboundSeqDuplicate`
  - `InboundSeqEpochReset`
  - `InboundSeqMissingFields`

Validation gate for Phase 4:

- Unit tests covering: in-order, single-gap-filled, single-gap-
  timeout, duplicate, epoch reset, buffer overflow, missing fields.
- Integration: a fault-injection test that delivers envelopes
  intentionally reordered (e.g., via a test-only provider that
  swaps adjacent messages with probability 0.5) and asserts no
  reactions are lost.

### Phase 5: Cursor checkpointing

Persist cursors so leadership handoff resumes cleanly.

Files:

- `server/inbound_sequencer.go`: every N admitted envelopes or every
  T seconds, write `(remoteID, channelID, epoch, nextExpected)` to
  KV under `seq_cursor:<remoteID>:<channelID>`.
- `server/inbound.go`: on becoming active for a connection, load
  cursors for every channel known to that connection.
- New error codes:
  - `InboundSeqCheckpointWritten`
  - `InboundSeqCheckpointLoadFailed`
  - `InboundSeqCheckpointStale` (epoch mismatch on load; treat as
    fresh and reset)

Validation gate for Phase 5:

- Unit test simulating leadership handoff: cursor reloaded, stream
  resumes without duplicate dispatch.
- Docker test: stop one node, send envelopes, start the other node,
  assert no duplicate posts.

### Phase 6: Documentation + audit guide

- `CLAUDE.md`: update the "Backend Message Flow" section to mention
  the sequencer between unmarshal and dispatch.
- `implementation-plans/26-04-12-03-xml-wire-format-schema.md`:
  cross-reference the new fields.
- New `docs/audit-logging-sequence.md` (if `docs/` exists; otherwise
  README addendum): documents the eight `InboundSeq*` error codes,
  their meaning, and the operator playbook for each.

## Risks and open questions

1. **Active-node election primitive.** Plugin API exposes
   `OnPluginClusterEvent` and `KVSetWithOptions(... ExpireInSeconds)`
   but not a first-class leader primitive. The TTL-lease pattern
   works but has a worst-case dual-leader window of
   `lease_ttl + clock_skew`. NATS queue groups defend against this
   at the transport level; for Azure providers, the message ACK
   path (visibility timeout, peek-lock, blob lock) defends against
   double processing. Phase 2 must verify each provider's behavior
   under brief dual-subscription.
2. **Counter persistence atomicity.** `pluginapi.KV.CompareAndSet`
   is the right primitive but is per-key. If a sender crashes
   between increment and publish, the counter advances but the
   envelope never goes out, leaving a permanent gap. The receiver's
   gap-fill deadline will time out, log the audit line, and
   advance past. This is acceptable under the "audit on loss" rule
   the user confirmed. Worth a comment in the code.
3. **NATS core has no replay.** During active-node handoff, NATS
   messages emitted in the dead window are lost. This is the
   transport's existing behavior, not a regression, and it is
   covered by the gap-timeout audit log. Documented as a known
   transport limitation in Phase 6.
4. **Throughput cap from single-active-receiver.** One node
   processes all inbound for a given connection. For Cross Guard's
   expected load this is fine; document as a capacity assumption
   in Phase 6 with a forward path (per-channel sharding within the
   active node if it ever becomes the bottleneck).
5. **Epoch persistence.** If the sender persists the epoch in KV
   and reads it on restart, a transient KV failure could yield
   either a reused epoch (no rollback risk since the counter
   persists alongside) or a new epoch (forces receiver reset, no
   correctness issue). Lean toward "always generate a fresh epoch
   on `OnActivate`" for simplicity; persistence is an optimization
   only worth doing if it shows up in practice.

## Validation summary

Per phase the gate is a clean `make check-style`, a green
`go test ./server/... ./server/wire/...`, and the relevant
integration step. Cross-phase, the final gate before merge to main
is:

- `make test` clean
- `make docker-integration-test` clean
- `python3 -c "import xmlschema; ..."` validates all 20 fixtures
- A new fault-injection test in the docker env that reorders 50%
  of envelopes and asserts no reactions or acknowledgements are
  lost on the receiver side.

## Order of work

1. **Phase 1 lands first** as a standalone PR carrying the XSD
   update, the inert struct fields, the updated example fixtures,
   and the round-trip test extension. This unblocks compliance
   review of the wire format and is fully reversible.
2. Phases 2-6 land in order as separate PRs, each with the gates
   above. Phases 2 and 3 can land in either order (sender stamping
   is harmless until receiver enforces; receiver election is
   harmless until receiver enforces). Phase 4 depends on Phases 2
   and 3. Phases 5 and 6 depend on Phase 4.
