# Conform the plugin to the constrained XSD

## Context

`schema/crossguard.xsd` was generated by a
compliance validation tool to determine whether the Cross Guard wire
format is acceptable for use in classified environments. It is the
authoritative contract: every byte that crosses the domain boundary
must validate against it. The plugin code, fixtures, and tests must
conform; the schema does not move to accommodate the plugin.

Numeric caps (`maxLength`, `maxOccurs`) that are too tight for product
reality will be raised through a **separate, future plan**. This plan
is scoped to pattern and structural conformance only.

Validating the 21 fixtures in `schema/examples/` against the
constrained schema, all 21 fail. The failures group into:

- Producer bugs: the plugin emits values that violate the schema's
  patterns (TestID format, empty `TeamName`/`ChannelName` on test
  envelopes, colon-wrapped `OverrideIconEmoji`).
- Upstream-supplied values that *can* violate the schema in
  non-standard topologies (multi-hop relays, exotic email formats,
  remote-tagged usernames). The plugin currently forwards these
  verbatim.
- Fixture-only artifacts (synthetic IDs like `sm-01`, `remote-low`).

This plan changes the plugin and fixtures so all 21 examples validate
against the constrained schema, and adds defensive validation in the
wire layer so a non-conforming upstream value can never silently cross
the boundary.

## Scope

In scope:

- Producer-side code fixes in `server/` and `server/wire/` for the
  three values the plugin actively produces in non-conforming form.
- Defensive validation in the wire layer for upstream-supplied values
  that pattern-violate in unusual topologies. On mismatch: log at
  `LogError` and drop the offending sync record (user, post, or
  reaction). Never silent.
- Fixture regeneration so the example suite validates end-to-end.
- A CI gate that validates fixtures against `schema/crossguard.xsd`
  on every build.

Out of scope:

- Pattern, type, or structural changes to `schema/crossguard.xsd`
  (the compliance-authoritative schema).
- Numeric cap changes (`maxLength`, `maxOccurs`). A separate plan
  will negotiate those with the compliance team.

## Problem inventory

### P1: producer emits a value the schema rejects (active bugs)

| # | Element / type | Schema rule | Plugin behavior | Fix location |
|---|---|---|---|---|
| 1 | `TestID` | `MattermostIdType` (`[a-z0-9]{26}`) | `newID()` returns `test-<unix_nano>` | `server/connections.go:69-71` |
| 2 | `TeamName`, `ChannelName` on test envelopes | `SlugType`, ≥ 1 char | `buildTestEnvelope` leaves both empty | `server/connections.go:52-65` |
| 3 | `OverrideIconEmoji` | `EmojiNameType` (`[A-Za-z0-9_\-\+]{1,64}`) | Forwarded as `:white_check_mark:` from upstream `override_icon_emoji` prop | `server/wire/post.go::PostPropsFromModel` |

### P2: defensive validation for upstream-supplied values

These values come from the upstream framework. In a typical
point-to-point Cross Guard deployment they conform; in unusual
topologies they may not. The wire layer must reject non-conforming
values rather than silently forward them.

| # | Element | Schema rule | When non-conformance can arise | Disposition on mismatch |
|---|---|---|---|---|
| 4 | `User.Username` | `UsernameType` (`[a-z0-9][a-z0-9_\-\.]{0,63}`) | The user was originally created on a remote, synced into this server (the framework appends `:<remoteID>` locally), and is now being re-relayed onward. Single-hop deployments never produce this. | Resolve-then-truncate ladder (see below). Drop only if neither path yields a conforming value. |
| 5 | `UserProps/RemoteUsername` | `UsernameType` | The framework can store a host-style remote identifier in this prop (e.g. `alice@source`) during multi-hop tracking. Single-hop deployments produce a plain username. | Drop the prop key only; the user record stays. |
| 6 | `User.Email`, `UserProps/RemoteEmail` | `EmailType` permissive RFC-style pattern | Schema rejects apostrophes (`o'brien@company.com`) and other RFC-5322 atext characters in the local part, IDN/Unicode local parts or domains, underscores in domains, IP-literal hosts, and quoted local parts. The apostrophe case is the most likely real-world hit; the others are rare. | Drop the sync record (user). For `RemoteEmail` specifically, drop the prop key only; the user record stays. |

Disposition is "never silent": every mismatch logs. Drops of full
sync records (user, post, reaction) log at `LogError`; recoveries
via sanitization (the resolve-then-truncate ladder, prop-key drops)
log at `LogWarn` so operators can see them without being paged.

### Username resolve-then-truncate ladder (P2.4 detail)

A colon-bearing `Username` is recoverable rather than fatal: the
upstream framework stamps the user's original (pre-tagged) username
into the `RemoteUsername` user-prop when it ingests a remote user.
The wire-side resolution order:

1. **As-is.** If `u.Username` matches `UsernameType`, use it verbatim.
2. **Resolve via RemoteUsername prop.** Else, if `u.Props
   ["RemoteUsername"]` is non-empty and matches `UsernameType`, use
   *that* as the wire `Username`. This is the normal path for users
   that originated on another server and are being synced outbound;
   no log is needed (it is the prop's reason for existing).
3. **Truncate at the first colon.** Else, if `u.Username` contains
   `:`, take everything before the first colon as the candidate. If
   the candidate matches `UsernameType`, use it. Log at `LogWarn`
   (`WireUsernameTruncatedAtColon`) — reaching this branch means the
   `RemoteUsername` prop was missing or itself non-conforming, which
   indicates upstream data inconsistency worth flagging.
4. **Drop.** Otherwise (no colon, or candidate still doesn't match),
   return `nil` and log at `LogError`
   (`WireUserDroppedNonConformingUsername`). The caller continues with
   the envelope minus the inline user.

This ladder is independent of the `RemoteUsername` prop's own wire
validation: the prop is still validated against `UsernameType`
separately at step (5) below, and its drop disposition stays
"drop the prop key" (P2.5). When the ladder consumes
`RemoteUsername` at step 2, it does not alter the prop's outbound
emission.

### P3: fixture-only failures

The 21 fixtures use hand-typed synthetic placeholders that don't match
`mmModel.NewId()` shape: `<Id>sm-NN</Id>`, `<RemoteId>remote-low</
RemoteId>`. They must be regenerated with 26-char IDs.

## Phase A: producer-side bug fixes

Land each item as its own commit; the diffs are small and individually
reviewable.

1. **TestID format** (P1.1). In `server/connections.go`, replace
   `newID()` with `mmModel.NewId()`. Drop the now-unused `fmt`/`time`
   imports if appropriate. Update `server/configuration_test.go:444`
   (`TestID: "abc-123"`) and any other tests that hard-code synthetic
   test IDs to use `mmModel.NewId()` too.

2. **Test envelope team/channel slugs** (P1.2). In `buildTestEnvelope`
   (`server/connections.go:52-65`), populate `TeamName` and
   `ChannelName` with a `SlugType`-conforming sentinel. The connection
   name is already `SlugType` and is meaningful, so reuse it for both
   fields. Receiver-side handling of test envelopes already ignores
   team/channel scope (`inbound.go:145` only logs `conn_name` and
   `test_id`), so this is a one-line cosmetic change.

3. **Icon emoji canonicalization** (P1.3). In
   `server/wire/post.go::PostPropsFromModel`, strip leading and
   trailing `:` from the `override_icon_emoji` value before assigning
   to `OverrideIconEmoji`. In `PostProps.ToModel()`, re-add the colons
   when materializing back into upstream `Props`, since downstream
   Mattermost expects the `:emoji:` form. Add a wire round-trip test.

## Phase B: defensive validation for upstream-supplied values

Add a small validator package, `server/wire/validate.go`, that
exposes the schema-derived regexes once so they don't drift:

```go
var (
    usernamePattern = regexp.MustCompile(`^[a-z0-9][a-z0-9_\-.]{0,63}$`)
    emailPattern    = regexp.MustCompile(`^[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}$`)
    // ...
)
```

These mirror the constrained XSD verbatim; the file has a header
comment pointing at the XSD as the source of truth and a `// keep in
sync with schema/crossguard.xsd` annotation on
each pattern.

Add new error codes in the wire-package range of
`server/errcode/codes.go`:

- `WireUserDroppedNonConformingUsername` (Error) — Username can't be
  recovered via the ladder.
- `WireUserDroppedNonConformingEmail` (Error) — Email pattern
  mismatch; whole user dropped.
- `WireUsernameTruncatedAtColon` (Warn) — colon-bearing Username
  sanitized by truncation (ladder step 3); indicates the
  `RemoteUsername` prop was missing or non-conforming.
- `WireUserPropDroppedNonConforming` (Warn) — an individual
  `UserProps` key (`RemoteUsername` or `RemoteEmail`) failed
  validation and was dropped; user record stayed.
- `WirePostDroppedNonConforming` (Error, reserved) — symmetric
  coverage for `Post` once a future field opens the same risk.
- `WireReactionDroppedNonConforming` (Error, reserved) — same for
  `Reaction`.

Wire-layer logging uses `slog` indirection through the existing
plugin logger; `server/wire/` does not have direct access to
`p.API`, so introduce a `WireLogger` interface in
`server/wire/validate.go` (methods `Warn(code, kv...)`,
`Error(code, kv...)`) and accept it as a parameter to
`UserFromModel` and `UserPropsFromModel`. The plugin wires up the
real logger in `transport.go::buildOutboundEnvelopes` and call
sites; tests inject a recording mock. Log K/V pairs include the
user ID and the validation outcome flag (`"path": "remote_prop"` or
`"path": "truncate"`); per CLAUDE.md, **never log the username or
email value itself**.

Apply validation:

1. **`UserFromModel`** (`server/wire/user.go:102`) signature change:
   ```go
   func UserFromModel(u *mmModel.User, log WireLogger) *User
   ```
   Before constructing the wire `*User`:
   - Run the **Username resolve-then-truncate ladder** (see P2.4
     detail above). If the ladder yields a conforming value, set
     `out.Username` to it; otherwise return `nil` with
     `WireUserDroppedNonConformingUsername`.
   - Validate `u.Email` against `emailPattern`. On failure, return
     `nil` with `WireUserDroppedNonConformingEmail`.

   Callers in `buildOutboundEnvelopes` already tolerate a `nil`
   user; the post still ships (so the post is not lost), the
   inline user entry is just absent, and the receiver resolves
   identity via its existing flow.

2. **`UserPropsFromModel`** (`server/wire/user.go:29-43`) signature
   change to accept `WireLogger`. Per-prop validation: if
   `RemoteUsername` fails `usernamePattern` or `RemoteEmail` fails
   `emailPattern`, drop that prop key only (the user record is
   still emitted with the remaining props, since the props are
   individually optional in the schema). Log at Warn with
   `WireUserPropDroppedNonConforming` and the prop name.

3. **Caller-side coverage.** In `buildOutboundEnvelopes`, when
   `UserFromModel` returns `nil`, the envelope is still constructed
   without the inline user. Add a sibling log call at `LogError`
   noting the post's ID and the dropped user ID so the operator can
   correlate the wire-layer drop with the post that triggered it.
   This is the per-message audit signal required by "never silently
   drop."

4. **Tests.** Add unit tests in `server/wire/user_test.go`
   enumerating the acceptance / sanitization / rejection matrix:
   - Username as-is: accepted (`alice`, `bob-2`, `c.d`), rejected
     (`BadCaps`, `with space`, empty, leading `_`).
   - Username via ladder step 2: `alice:remoteABC` + `Props
     ["RemoteUsername"]="alice"` → wire `Username="alice"`, no log
     emitted (normal outbound path for remote-originated users).
   - Username via ladder step 3: `alice:remoteABC` with empty /
     non-conforming `RemoteUsername` prop → wire `Username="alice"`,
     warn logged.
   - Username drop: `:starts-with-colon`, `Bad:remoteABC` (truncate
     yields `Bad` which still fails), no colon and non-conforming
     → user dropped, error logged.
   - Email: accepted (`firstname.lastname@company.com`,
     `user+tag@example.org`), rejected (`o'brien@company.com`,
     `user@münchen.de`, `user@my_company.internal`,
     `user@[192.0.2.1]`).
   Use a recording `WireLogger` mock to assert each scenario emits
   the right error code at the right level.

## Phase C: regenerate fixtures

Land after Phase A so the fixture generator runs against conforming
producers.

1. Audit `server/examples_roundtrip_test.go`. Replace synthetic seeds
   (`sm-NN`, `remote-low`, hand-typed `epochNNaaaaa...`) with literal
   26-char strings matching `[a-z0-9]{26}`. Use fixed literals so the
   regenerated fixtures are stable across CI runs and reviewable in
   diff.
2. Run `UPDATE_EXAMPLES=1 go test -run TestExampleFiles ./server/`.
   Commit the regenerated `schema/examples/*.xml` files.
3. Confirm: `for f in schema/examples/*.xml; do xmllint --noout
   --schema schema/crossguard.xsd "$f"; done` reports zero failures.

## Phase D: CI gate

Extend `TestExampleFiles` (or add a sibling test in the same file) so
that, when `xmllint` is available on `PATH`, it validates every
fixture against `schema/crossguard.xsd`:

```go
schema := "../schema/crossguard.xsd"
for _, fixture := range fixtures {
    // exec xmllint --noout --schema <schema> <fixture>
    // fail on non-zero exit
}
```

Skip the test when `xmllint` is absent so developer environments
without libxml2 stay green. CI installs `libxml2-utils` so the gate
runs in CI. This prevents future fixture regeneration or wire-type
edits from producing wire content the strict schema would reject in
a compliance audit.

## Validation gate

The change is complete when:

1. `make check-style` is clean.
2. `make test` is green.
3. `for f in schema/examples/*.xml; do xmllint --noout --schema
   schema/crossguard.xsd "$f"; done` reports zero failures.
4. The CI gate from Phase D passes locally.
5. A short note in
   `implementation-plans/26-04-12-03-xml-wire-format-schema.md`
   records that `schema/crossguard.xsd` is the producer's target
   and that any change to a wire struct in `server/wire/` must be
   re-validated against it.

## Follow-up (separate plan)

Numeric caps (`maxLength`, `maxOccurs`) in the constrained schema
will be negotiated with the compliance team via a separate plan.
Items likely to come up:

- `MentionTransformsType.Transform/@maxOccurs="100"` (plausible to
  exceed in long-lived busy channels).
- Any `xs:maxLength` that turns out tighter than the corresponding
  upstream Mattermost product limit.

That work is gated on real-world drop telemetry collected after
Phases A-D land in production: the new error codes in `errcode`
let operators see exactly which patterns and caps are hitting in
the field, which makes the compliance conversation evidence-based.
