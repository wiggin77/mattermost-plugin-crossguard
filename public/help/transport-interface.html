Transport Interface Reference

Wire protocol and message schemas for Cross Guard message transports

Overview

Cross Guard supports four transport providers for relaying messages between Mattermost instances: NATS, Azure Queue Storage, Azure Blob Storage (batched WAL), and Azure Service Bus. Each provider has different delivery guarantees, latency characteristics, and infrastructure requirements. The plugin integrates with Mattermost's shared-channels framework, so outbound messages enter the plugin through the framework's sync hooks (OnSharedChannelsSyncMsg, OnSharedChannelsAttachmentSyncMsg, OnSharedChannelsProfileImageSyncMsg, OnSharedChannelsPing), and inbound messages exit back into the framework via ReceiveSharedChannelSyncMsg. Sync content (posts, users, reactions, statuses, membership changes, acknowledgements, mention transforms) is wrapped in an XML envelope (or JSON, per the connection's message_format setting) and delivered through the transport. File attachments and profile images do not ride the XML envelope; they flow through a separate file-upload channel (UploadFile/WatchFiles on QueueProvider) with metadata carried as X-Crossguard-* headers on the blob.

QueueProvider Interface

Every transport implements the QueueProvider interface defined in server/provider.go. The interface is intentionally small: a publish / subscribe pair for sync envelopes, a parallel pair for file uploads, a MaxMessageSize hint that the splitter respects, an IsConnected health probe for the ping hook, and a Close. Anything provider-specific (queue creation, lease management, batch flushing, dead-letter handling) lives behind these methods. 

type QueueProvider interface {
    Publish(ctx context.Context, data []byte) error
    Subscribe(ctx context.Context, handler func(data []byte) error) error
    UploadFile(ctx context.Context, key string, data []byte, headers map[string]string) error
    WatchFiles(ctx context.Context, handler func(key string, data []byte, headers map[string]string) error) error
    MaxMessageSize() int
    IsConnected() bool
    Close() error
}
PublishSends a fully marshalled TransportEnvelope (XML or JSON bytes) over the transport. The caller has already applied Epoch and Sequence.
SubscribeDelivers incoming envelope bytes to the inbound pipeline. The handler may return an error to defer acknowledgement so the transport retries (Azure Queue dequeue lease, Service Bus PeekLock abandon, etc.).
UploadFileCarries raw file bytes (attachment or profile_image) with metadata headers. The key follows a stable pattern: attachment/{postID}/{fileID} or profile_image/{userID}.
WatchFilesDelivers each new file blob to a handler with the same key and headers the sender used. The handler discriminates the file kind from the X-Crossguard-Kind header.
MaxMessageSizeHard upper bound on the byte length of a single Publish argument. 0 means "no practical limit"; the plugin treats anything > 0 as a budget the envelope splitter must respect.
IsConnectedCheap health probe used by OnSharedChannelsPing to surface outbound-unhealthy / inbound-unhealthy audit events without forcing a publish.
CloseReleases any provider-side resources (NATS subscriptions, Azure SDK clients, background poll goroutines). Idempotent.
NATSMaxMessageSize() == 0 (no plugin-enforced cap; NATS server default applies)
Azure QueueMaxMessageSize() == 48000 bytes (the plugin caps below 64 KB so Base64 expansion fits the 64 KB Azure Queue wire limit)
Azure BlobMaxMessageSize() == 0 (the WAL buffer multiplexes many envelopes per batch blob; the cap is the blob size, not the envelope size)
Azure Service BusMaxMessageSize() == max_message_size_bytes (default 192000; configurable up to 100 MiB on Premium tier)

Message Envelope

sync_msg and test envelopes ride this schema on the wire. attachment and profile_image uploads do not use this envelope at all (see File-Upload Headers below). The outbound connection's message_format setting selects the serialization (XML or JSON); inbound is auto-detected by the first non-whitespace byte (< for XML, { for JSON; a leading UTF-8 BOM on XML is stripped before detection).

JSON field names exactly mirror the XML element and attribute names defined in schema/crossguard.xsd, so the two serializations are field-for-field equivalent. The reference Go type is TransportEnvelope in server/transport.go.

ENVELOPE CrossGuardEnvelope

Schema

versionint, required, attribute. Wire-format version, always 1 today. Carried as an XML attribute on the root <CrossGuardEnvelope> element; in JSON, a top-level field.
typestring, required, attribute. One of the four envelope types. Determines which payload field is present (or, for attachment/profile_image, that this envelope is not used at all).
ConnNamestring, required. Outbound connection name on the sender (URL-safe slug, max 96 chars). The receiver uses this to scope per-channel sequence numbers and to dispatch audit events.
Timestampstring, required. UTC timestamp in RFC 3339 format (e.g. 2026-03-27T14:30:00Z). Defaults to time.Now().UTC() at marshal time when the caller leaves it empty.
Epochstring, required on sender-originated envelopes. 26-character Mattermost ID ([a-z0-9]{26}) identifying the sender process generation, so the receiver can correlate sequence numbers across restarts. Stamped on both sync_msg and test envelopes.
Sequenceunsigned 64-bit int, required on sync_msg only. Per-(ConnName, ChannelId) monotonic counter within an epoch. Lets the receiver detect duplicates and reorder short gaps. Absent on test envelopes (no channel scope).
TeamNamestring, required. Sender's team name (URL-safe slug, max 96 chars). On test envelopes this carries the connection name as a placeholder so the field passes XSD validation; the receiver ignores team and channel scope for type=test.
ChannelNamestring, required. Sender's channel name (URL-safe slug, max 96 chars). On test envelopes this carries the connection name as a placeholder.
SyncMsgobject, optional. Present when type is sync_msg. Carries the shared-channels sync payload. See SyncMsg Payload.
TestIDstring, optional. Present when type is test. A 26-character Mattermost ID generated by the test-connection handler; the receiver echoes it into its audit log.

Envelope Types

The type attribute is the envelope discriminator. The four constants are defined in server/transport.go. Two ride the XML envelope above; two are file uploads with headers instead.

Type ValueGo ConstantCarrierDescription
sync_msg TransportTypeSyncMsg XML envelope, SyncMsg payload Shared-channels sync. Carries at most one Post plus optional non-post content (users, reactions, statuses, membership changes, acknowledgements, mention transforms) from one sync cycle.
test TransportTypeTest XML envelope, TestID field Connectivity check sent by the test-connection handler. Carries Epoch and TestID; the receiver echoes both into audit logs.
attachment TransportTypeAttachment File upload, X-Crossguard-* headers Raw file bytes for a Post attachment. Not an XML envelope. Metadata travels as HTTP-style headers on the file blob. Emitted from OnSharedChannelsAttachmentSyncMsg.
profile_image TransportTypeProfileImage File upload, X-Crossguard-* headers Raw image bytes for a synced user's avatar. Not an XML envelope. Emitted from OnSharedChannelsProfileImageSyncMsg.

SyncMsg Payload

The SyncMsg element carries the shared-channels sync content. The plugin uses pruned, plugin-owned wire types (under server/wire/); each is a subset of the corresponding upstream mmModel type with source-only fields stripped and receiver-overwritten fields dropped. Field order inside <SyncMsg> is fixed: Id, ChannelId, Users, Post, Reactions, Statuses, MembershipChanges, Acknowledgements, MentionTransforms.

Each sync_msg envelope carries at most one Post. The sender splits each upstream sync cycle into one envelope per Post; non-post content from the same cycle (orphan reactions, memberships, statuses, and the users they reference) rides a single optional metadata envelope with no <Post> child. This one-post-per-envelope contract is the compliance-content-inspection blast-radius control: rejecting one post does not lose other content as collateral damage.

File-Upload Headers

attachment and profile_image envelopes do not ride the XML transport envelope. The plugin uploads raw file bytes through QueueProvider.UploadFile; metadata travels as HTTP-style headers on the file blob. Each provider maps these headers to its native metadata mechanism: NATS JetStream Object Store uses nats.Header, Azure Blob uses blob metadata, Azure Service Bus uses metadata on the blob sidecar container. The receiver reads them on the WatchFiles event and reconstructs the file context. Header names are case-insensitive on the wire.

HeaderRequired ForDescription
X-Crossguard-KindbothDiscriminator: attachment or profile_image.
X-Conn-NamebothOutbound connection name on the sender (URL-safe slug, max 96 chars).
X-FilenamebothOriginal filename. profile.png for profile images.
X-Team-NameattachmentSender team name. The receiver runs the same rewrite-then-by-name resolution the message envelope uses.
X-Channel-NameattachmentSender channel name. Same rewrite path.
X-Post-Idattachment26-character Mattermost ID of the post this file belongs to.
X-File-InfoattachmentBase64-encoded JSON mmModel.FileInfo. Base64 wraps the JSON so it survives provider metadata-encoding rules (Azure Blob metadata is HTTP-header-grade; NATS uses nats.Header).
X-User-Idprofile_image26-character Mattermost ID of the synced user whose avatar is being uploaded.

Object keys follow a stable pattern: attachment/{postID}/{fileID} for attachments and profile_image/{userID} for profile images. The receiver uses the key prefix and the X-Crossguard-Kind header in tandem so mistyped uploads cannot escape their lane.

Connection Behavior (NATS)

The plugin uses the standard NATS client (nats.go) with its default reconnect machinery. The shared-channels framework owns the retry semantics for sync envelopes: a failed OnSharedChannelsSyncMsg call returns an error and leaves the framework cursor unadvanced, so the framework retries on its own schedule. The plugin does not add a publish-side retry loop. Inbound work is deliberately serial under the single-active-receiver lease, so there is no relay semaphore.

Inbound Active Lease 45 s TTL, 15 s renewal KV TTL lease held by the active inbound receiver. Only one node in the cluster subscribes per inbound connection at a time; failover is automatic.

Each uploaded object carries a set of custom NATS headers that the receiving instance uses to route the file to the correct context. File Filtering

Each connection can independently filter files by extension using three modes:

ModeBehaviorExample
"" (empty, default) No filtering. All files pass. "file_filter_mode": ""
"allow" Only files with listed extensions are relayed. "file_filter_mode": "allow", "file_filter_types": ".pdf,.docx"
"deny" Files with listed extensions are blocked. "file_filter_mode": "deny", "file_filter_types": ".exe,.bat"

Extensions are case-insensitive and a leading dot is optional (both pdf and .pdf are accepted). Filters are evaluated independently on outbound (before upload) and inbound (before download).

JetStream Requirement

File transfer requires a JetStream-enabled NATS server. If the NATS server does not have JetStream enabled, file transfer will fail silently with errors logged. Core NATS text relay is not affected.

Format Selection: XML and JSON

Cross Guard supports two wire serializations. The outbound connection's message_format setting (xml or json) selects which one outbound envelopes use. Inbound connections are auto-detected; a single inbound connection can accept envelopes in either format. JSON field names exactly mirror the XML element / attribute names defined in schema/crossguard.xsd, so the two serializations are field-for-field equivalent.

Key Differences Between Formats

AspectXMLJSON
Root <CrossGuardEnvelope version="1" type="..."> (no namespace; version and type are attributes) Top-level object with version and type fields
Field names CamelCase elements (<ConnName>, <Timestamp>, <SyncMsg>); lowercase root attributes (version, type) Same names, same casing (mirror)
Character escaping XML entity escaping (&lt;, &gt;, &amp;, &#xA; for newlines) JSON string escaping
Schema schema/crossguard.xsd is the normative XML Schema; every outbound payload is schema-valid by construction OpenAPI 3.1 schema in schema/crossguard-api.yaml
Empty containers Omitted entirely (no empty <Users></Users>) Omitted entirely (no "Users": {})
Map ordering Sorted by key (XML <Entry> / <Transform> children) Sorted by key (deterministic JSON object property order)
Size overhead Baseline (closing tags) 10-20% smaller in typical envelopes

Inbound Auto-Detection

Inbound connections do not require format configuration. The plugin inspects the first non-whitespace byte of each incoming envelope: < selects the XML parser, { selects the JSON parser. A single inbound connection can therefore accept envelopes from sources that use either format.

BOM Handling

XML output does not include a Byte Order Mark. If an upstream device (e.g. a CDS shuttle) prepends a UTF-8 BOM (0xEF 0xBB 0xBF) to the message, the inbound parser strips it before format detection so BOM-prefixed XML still parses correctly. JSON envelopes do not carry a BOM.

Azure Queue Storage Transport

Overview

The Azure provider uses Azure Queue Storage for message delivery and Azure Blob Storage for file transfer. Unlike NATS pub/sub, Azure uses a polling model where the inbound side periodically checks the queue for new messages.

Auth is via an Azure Storage shared-key credential (legacy default) or an Azure AD Service Principal (Phase 1 supports the client-credentials / client-secret flow). See Azure Service Principal Authentication in the admin guide for the SP field reference, the minimum RBAC roles, and the deployment guidance (including the no-auto-create rule in SP mode).

Message Lifecycle

  1. Outbound serializes the message envelope (JSON or XML)
  2. Payload is Base64-encoded and enqueued to Azure Queue Storage
  3. Inbound polls the queue every 5 seconds
  4. Messages are dequeued with a 5-minute visibility timeout
  5. On successful processing, the message is deleted from the queue
  6. On handler error, the message becomes visible again after the timeout for retry
  7. Malformed messages (invalid Base64) are deleted immediately to prevent reprocessing loops

Azure File Transfer (Blob Storage)

When file_transfer_enabled is true and a blob_container_name is configured, file attachments are transferred via Azure Blob Storage.

Upload (Outbound)

  1. File data is uploaded as a block blob to the configured container
  2. The blob key follows the format: {post_id}/{unique_id}
  3. Headers (post ID, connection name, filename) are stored as blob metadata under the crossguard_headers key
  4. Metadata is a Base64-encoded JSON object: {"headers": {"X-Post-Id": "...", "X-Conn-Name": "...", "X-Filename": "..."}}

Download (Inbound)

  1. The blob watcher polls the container every 15 seconds using a list operation
  2. New blobs (after the last processed marker) are downloaded
  3. Headers are extracted from the crossguard_headers metadata
  4. After successful processing, the blob is deleted
  5. The marker only advances after a successful delete, ensuring blobs are re-listed on failure

Azure Blob Storage Transport

Overview

The Azure Blob provider is a second Azure transport that does not use Azure Queue Storage at all. Instead of enqueuing one queue message per relay event, the outbound side appends messages to an in-memory write-ahead log (WAL) and periodically seals and uploads the WAL as a single batch blob. The inbound side polls the blob container, takes a short-lived lease on each batch blob, processes its messages, and deletes the blob. File attachments are uploaded as deferred file blobs into the same container.

Use this transport when you want to amortize blob operations across many messages, avoid per-message queue charges, or when the queue service is unavailable in your environment. Expected end-to-end latency is bounded by flush_interval_seconds.

Auth is via an Azure Storage shared-key credential (legacy default) or an Azure AD Service Principal. See Azure Service Principal Authentication in the admin guide for the SP field reference, the minimum RBAC role (Storage Blob Data Contributor), and the no-auto-create rule in SP mode.

Message Lifecycle

  1. Outbound appends each relay event to an in-memory WAL buffer.
  2. Every flush_interval_seconds (default 60), the buffer is sealed and uploaded as a batch blob under a time-ordered key.
  3. Inbound lists the container on a poll cycle and, for each batch blob, acquires a lease.
  4. While the lease is held, messages are delivered to the inbound handler.
  5. On success, the blob is deleted and the lease is released. On failure, the lease expires and another poller may retry.
  6. If a lease grows older than blob_lock_max_age_seconds (default 300), it is considered stale and another inbound node may break the lease and take over.

Azure Service Bus Transport

Overview

The Azure Service Bus provider uses an AMQP-based Service Bus queue for message delivery and an optional Azure Blob Storage sidecar container for file transfer. Unlike the Azure Queue provider, Service Bus uses PeekLock receive semantics with server-side delivery counts and a native dead-letter queue (DLQ). Authentication is via a SAS connection string (legacy default) or an Azure AD Service Principal. In connection-string mode the blob sidecar takes its own shared-key credential separate from the Service Bus namespace; in Service Principal mode the blob sidecar inherits the parent SP credential so a single AAD identity covers both AMQP and blob access.

See Azure Service Principal Authentication in the admin guide for the SP field reference (including the additional service_bus_namespace required in SP mode), the minimum RBAC roles (Azure Service Bus Data Sender + Azure Service Bus Data Receiver on the queue, plus Storage Blob Data Contributor on the blob account when file transfer is enabled), and the credential-inheritance rule for the blob sidecar.

The plugin does not auto-create queues. Pre-create the queue in the Azure portal or via ARM/Terraform with your chosen LockDuration and MaxDeliveryCount before saving the connection. Lock duration is an entity property; the plugin cannot set it.

Message Lifecycle

  1. Outbound serializes the message envelope (JSON or XML) and sends it via the Service Bus SDK.
  2. Oversized payloads (above max_message_size_bytes) are rejected at the client boundary before send.
  3. Inbound receives messages in batches (up to 32) under PeekLock.
  4. Messages with DeliveryCount > 1 log a WARN (error code 26004) so operators can detect poison-message buildup before DLQ moves happen.
  5. Empty-body messages are dropped via Complete to avoid infinite redelivery loops (error code 26005).
  6. On handler success, the message is Completed. On handler error, the message is Abandoned; Service Bus increments DeliveryCount and redelivers.
  7. After MaxDeliveryCount is exceeded, Service Bus auto-moves the message to the queue's dead-letter sub-queue. The plugin does NOT inspect or process DLQ messages; use the Azure portal, az servicebus queue message, or Azure monitoring to inspect the DLQ.

Service Bus File Transfer (Blob Sidecar)

When file_transfer_enabled is true and the blob sidecar fields are configured, file attachments are transferred via Azure Blob Storage using the same upload/download mechanics as the Azure Queue provider ({post_id}/{unique_id} blob keys, Base64-encoded JSON metadata under the crossguard_headers key). Service Bus queues themselves are message-only; files never flow through the queue.

Loop Prevention and Delivery Guarantees

Cross Guard rides on the shared-channels framework's intrinsic loop prevention (every received user carries a non-empty RemoteId; the framework refuses to re-sync content marked as remote) and adds three plugin-level guards:

  • Per-remote outbound suppression. The outbound hook resolves the target connection via connNameForRemote(rc.RemoteId) and refuses to send back to the remote a message originated from. A sync envelope that arrived from connection A never re-leaves on connection A.
  • Connection linkage validation. Envelopes are only published to outbound connections that are explicitly linked to the originating team. Inbound envelopes are only processed if the target team and channel are linked to the receiving inbound connection; otherwise the inbound handler posts an Accept / Block prompt rather than applying the content.
  • Inbound deduplication. The inbound sequencer keys on (Epoch, ConnName, ChannelId, Sequence) and drops any envelope it has already admitted. Combined with the single-active-receiver lease (only one node per cluster subscribes at a time), this catches duplicates from at-least-once providers and replays from a sender restart.

System messages (channel join / leave, header changes, etc.) ride the SyncMsg.MembershipChanges container or as system-typed Posts; both are relayed normally and routed by the framework on the receiving side. The plugin does not filter them out, since the framework needs the events to keep its synced channel membership view current.
